# Lattely

A web app for discovering specialty coffee shops in Barcelona.

## Run locally

Use Node.js 24 or newer and pnpm 11.5.1 (the version pinned in `package.json`).

```sh
pnpm install
pnpm dev
```

Open <http://localhost:3000>. No account, environment variables, or external services are needed.

## Checkpoint 1: the application shell

The application shell provides the Lattely heading, an introduction, and a private-development notice.

When a browser requests `/`, Next.js uses `src/app/page.tsx` for the page content and wraps it in `src/app/layout.tsx`, which supplies the document's `<html>` and `<body>` elements and page metadata. Both are Server Components by default. This page has no client-side state or data requests; Next.js can render it to static HTML during the production build.

`src/app/globals.css` imports Tailwind and defines the shadcn Stone theme tokens. The PostCSS configuration makes Tailwind turn the utility classes in the components into CSS.

### Configuration and generated files

- `package.json`: commands and pinned direct dependencies.
- `tsconfig.json`: TypeScript settings, including strict checking.
- `postcss.config.mjs`: the Tailwind build plugin.
- `pnpm-lock.yaml`: generated by pnpm; committed to keep dependency resolution reproducible.
- The marked Next.js block in `AGENTS.md`: generated by `next dev`; points coding agents to the installed framework documentation and preserves the repository's existing instructions.
- `next-env.d.ts` and `.next/`: generated by Next.js; ignored by Git. Do not edit them.
- `node_modules/` and `*.tsbuildinfo`: installed packages and TypeScript's checking cache; ignored by Git.

The application and configuration files were written directly using the standard Next.js setup; there is no generated starter UI to learn or remove.

## Checkpoint 2: one sample coffee shop

The home page displays **Sample Coffee** in **Gràcia, Barcelona**, with a short description of its specialty coffee. Both the page notice and the shop label identify it as fictional sample data for private development.

The shop is a plain `sampleShop` object in `src/app/page.tsx`. The page reads its name, neighborhood, and description directly into semantic HTML. There is no database, API request, or browser storage; changing the sample means editing that object. The production build includes its values in the rendered HTML, so visitors can view the shop without an account.

## UI components

shadcn/ui is configured in `components.json`, with component source in `src/components/ui/` and the `@/*` alias pointing to `src/`. The CLI copied the Card, Badge, and Alert components from the official registry; they are local source that we can edit and format. They use the `cn` class-merging utility, Radix Slot for composition, and `class-variance-authority` for variants.

The shop uses Card, CardHeader, CardTitle, CardDescription, and CardContent. Badge identifies fictional data. Alert presents the development notice with `role="note"`, since this static information should not interrupt a screen reader as an urgent alert. Its title wraps on narrow screens. The page keeps a real `<main>`, `<article>`, `<h1>`, and `<h2>`; shadcn components do not replace those semantic choices.

The layout uses Tailwind breakpoints for spacing and shadcn's semantic color tokens for consistent contrast. Accessibility and responsiveness still need checking when we compose components. This page has no interactive controls or keyboard behavior to implement.

Add standard components as features need them using `pnpm dlx shadcn@4.23.0 add <component>`, then review the generated files and dependencies and run the checks below. Keep feature-specific compositions in the feature folders described in `docs/agents/tech-stack.md`.

## Checkpoint 3: database-backed coffee shop list

The home page now reads shop IDs and names from the `coffee_shops` table with Drizzle on the server. It sorts by name, shows a useful empty state when the table has no rows, and gives a generic message if the query fails. `DATABASE_URL` stays server-side. The seed and browser-test commands explicitly use the Neon `development` branch; the production branch is not used.

## Verify

```sh
pnpm format:check
pnpm typecheck
pnpm build
pnpm test:e2e
```

`pnpm test:e2e` seeds two deterministic rows in the development branch, then starts the built app and checks that both names are rendered from the database. To inspect the page manually, run `pnpm start` and open <http://localhost:3000>.

Authentication, search, and hosting configuration are deferred.
